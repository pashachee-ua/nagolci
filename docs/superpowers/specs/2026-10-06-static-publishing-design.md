# NA GOLCI: статический сайт и отдельный редактор

Дата: 6 октября 2026. Проект: `site-wow`, GitHub `pashachee-ua/nagolci`.

## Цель и принятые решения

Публичная страница должна отдаваться готовым HTML, без запроса к D1 и серверного React-рендеринга при посещении. Мастер продолжает самостоятельно менять контент через существующий редактор. Сохранение создаёт черновик, отдельная публикация выпускает статическую версию. Это выбранная пользователем схема из обсуждения хостинга.

Сохраняем текущий дизайн, галерею, lightbox, отзывы, анимации, видео и украинский язык. Сайт пока закрыт для индексации; включение индексации и окончательные canonical URL выполняются при отдельной подготовке запуска с реальным доменом.

Первый этап выполняется локально в `site-wow`. Существующая публикация на chatgpt.site остаётся рабочей, перенос на другой хостинг и подключение домена выполняются после проверки новой реализации и настройки Cloudflare. Изменение DNS, создание облачных ресурсов и перенос существующих данных не входят в локальный этап.

## Варианты

1. **Статическая страница и отдельный Worker редактора — выбранный вариант.** Посетители получают готовый HTML и обычные статические ресурсы. Черновики, загрузки и публикация обслуживаются отдельно. Минус: выпуск контента требует сборки и раздельных настроек хостинга.
2. **Текущий SSR с кэшем.** Меньше изменений кода, но публичная часть сохраняет серверную зависимость, требуется корректная инвалидация кэша. Не выполняет выбранную цель полностью.
3. **Статическая страница с загрузкой контента через браузерный API.** Проще обновления, но основной контент отсутствует в начальном HTML и загрузка страницы зависит от API. Не выбираем.

## Структура

- Публичная часть: статический HTML, CSS, клиентский React для интерактивности; сборка Vite. Хостинг — Cloudflare Pages с GitHub и Deploy Hook.
- Редактор: существующий React Editor, отдельная клиентская сборка и Cloudflare Worker для `/api/content`, `/api/upload`, публикации и служебного получения снимка для сборки. У редактора отдельный origin, в будущем `admin.<домен>`; запросы редактора к его API остаются same-origin.
- D1: рабочий черновик, его revision и сведения о запросах публикации.
- R2: неизменяемые загруженные фотографии и снимки опубликованного контента.
- Публичные фотографии: существующие `public/images` входят в сборку; загруженные фотографии копируются из R2 в статический артефакт во время сборки. Посетители не обращаются к API редактора для получения фото.
- Общие компоненты и типы используются повторно. Не переписываем портфолио и не меняем CMS-модель ради нового хостинга.

## Статическая сборка

Сборка получает один валидированный снимок `SiteContent` и revision. Для локального запуска допускается явно выбранный seed из репозитория или JSON-файл. Production-сборка получает снимок публикации через защищённый серверный endpoint; при недоступности endpoint не подменяет его seed-данными.

HTML портфолио создаётся React на этапе сборки. Браузер гидратирует те же компоненты с тем же снимком. До загрузки JavaScript доступны основной текст, контакты, изображения и отзывы. Свайпы, lightbox, пауза анимаций, раскрытие отзывов и видео активируются после гидратации.

Снимок в HTML безопасно сериализуется: пользовательский текст не может завершить `<script>` или внедрить HTML. Год в футере и прочие меняющиеся при рендере значения должны совпадать между сборкой и гидратацией.

Выход: отдельная папка статического сайта с `index.html`, локальными ресурсами, служебным манифестом revision публикации и настройками заголовков. Не включает код админки, черновики, секреты или Worker. Сборка проверяет существование всех локальных изображений и видео. Некорректный контент или отсутствующее медиа приводят к ошибке до публикации.

Загруженные пути `/api/media/<uuid>.<ext>` преобразуются в локальные пути статического артефакта. Снимок редактора остаётся в прежней модели, преобразование выполняется только для публичного результата. Не удаляем ранее загруженные объекты при удалении работы из черновика: старая публикация может их использовать.

## Редактирование и публикация

`Сохранить` валидирует контент и сохраняет черновик с optimistic concurrency по revision. Сообщение не утверждает, что данные уже видны посетителям. Загрузка фото только добавляет объект и меняет рабочую форму; она не запускает сборку.

`Опубликовать` доступна для сохранённого черновика. Если форма изменена, интерфейс предлагает сначала сохранить. Запрос передаёт ожидаемую revision; устаревшая revision даёт конфликт, а не публикацию чужого черновика.

Сервер создаёт неизменяемый снимок выбранной revision и запись публикации, затем вызывает Deploy Hook. Секрет hook хранится только на Worker. Сборка читает снимок публикации, а не произвольно изменившийся черновик. Последующие сохранения не меняют уже отправленный снимок.

Разрешён один незавершённый выпуск одновременно. Повторное нажатие для того же выпуска возвращает его состояние без второго запуска. Для параллельного выпуска возвращается понятное сообщение о текущем процессе. Состояние Cloudflare и идентификатор deployment сопоставляются с опубликованной revision по манифесту артефакта. Только подтверждённый успешный deployment означает «Опубликовано»; принятие hook означает лишь «Запрошена публикация».

При ошибке hook или сборки черновик сохраняется, предыдущий сайт остаётся доступен. Есть возможность повторить выпуск после ошибки; секреты и внутренние ошибки не отображаются мастеру. Зависший выпуск сверяется с состоянием Cloudflare до повторного запуска.

Для первого локального этапа внешний запуск и статус проверяются с тестовым провайдером; реальный Cloudflare-провайдер подключается после появления проекта и необходимых настроек.

## Вход в редактор

Предлагаемый вариант: Cloudflare Access с разрешёнными email редакторов. Он заменяет текущую зависимость от заголовков авторизации ChatGPT. Это предложение для подтверждения при review спецификации.

Защищаем весь origin редактора, включая HTML и изменяющие API. Worker проверяет подпись Access JWT, issuer, audience, срок действия и email по серверному allowlist. Не доверяет одному заголовку с email. Служебный endpoint сборки использует отдельный серверный credential и отдаёт только снимок и требуемые медиа; не предоставляет операции редактирования.

Изменяющие запросы проверяют точный origin редактора, Content-Type и существующие ограничения размеров/типов данных. Отсутствующие production-настройки закрывают доступ; локальные обходы авторизации не должны работать в production. Публичная часть не требует входа.

## Что потребуется от аккаунта Cloudflare

Для подключения после локальной реализации: Pages-проект, Worker, D1 и R2, настройки Access и список email редакторов, Deploy Hook, ограниченные серверные credentials для сборки и проверки статуса публикации. Значения не коммитятся в Git. Конкретный домен можно добавить позднее; конфигурация не зашивает вымышленный домен.

Перед переносом нужно отдельно получить актуальные данные и загруженные медиа текущей опубликованной версии. Seed из Git не считается автоматически актуальным production-контентом.

## Проверки и критерии приёмки

1. Статический HTML содержит тексты, контакты и отзывы без JavaScript и без обращения к D1.
2. Клиентская сборка сохраняет галерею, lightbox, свайпы, отзывы, видео и доступность управления; нет ошибок гидратации на мобильном и широком экране.
3. Все медиа артефакта разрешаются локально; отсутствующие медиа и невалидный снимок останавливают сборку.
4. Сохранение черновика не меняет опубликованный результат; выпуск использует конкретную revision.
5. Конфликт revisions, повторное нажатие, параллельная публикация, ошибки hook/build и успешный выпуск проверены интеграционно.
6. Неавторизованные изменения, поддельная identity, чужой origin и превышение лимита загрузки отклоняются.
7. HTML и клиентский bundle не содержат credentials и не обращаются к draft API публично.
8. TypeScript и существующие тесты проходят; обе новые сборки воспроизводимы.
9. Локально проверена цепочка «сохранить → снимок → сборка → успешная публикация» с тестовым провайдером. Cloudflare deployment отдельно проверяется после настройки аккаунта.

## Границы

Не добавляем новые языки, визуальные изменения, обработку фотографий, аналитику, онлайн-запись или новый CMS. Не меняем индексирование в рамках миграции. Сначала проверяем новую схему локально, затем на тестовом адресе Cloudflare, после этого подключаем купленный домен.
